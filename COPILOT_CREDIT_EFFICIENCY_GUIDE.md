## How GitHub Copilot Pricing Works

Understanding token consumption and billing is fundamental to optimizing costs.

### Token Types and Pricing

When you use Copilot, the interaction consumes three types of tokens:

| Token Type | Description | Pricing Impact |
|-----------|-------------|-----------------|
| **Input Tokens** | Context sent to the model (code, instructions, history) | Charged at model's input rate |
| **Output Tokens** | Content generated by the model | Charged at model's output rate (typically higher) |
| **Cached Tokens** | Context the model reuses or stores | 10x cheaper than uncached input tokens |

### AI Credits and Cost Conversion

- **1 AI Credit = $0.01 USD**
- Each token is priced based on the model used
- Total token count is converted to AI Credits
- Prices are listed per 1 million tokens

### Key Cost Factors

The cost of any interaction depends on two primary factors:

1. **Model Selection** - Different models have vastly different per-token costs
2. **Token Consumption** - Input, output, and cached tokens all contribute to total cost

### Components That Consume Tokens

Every request to Copilot includes multiple components:

| Component | Purpose | Optimization Strategy |
|-----------|---------|----------------------|
| **System Instructions** | Core agent behavior | Keep stable within session (enables caching) |
| **Copilot Instructions** | Custom agent directives | Use focused, modular instructions |
| **Tool Schema** | Tool definitions and parameters | Use tool search (deferred loading) |
| **Conversation History** | Previous messages in session | Reuse sessions when possible |
| **File Contents** | Code being analyzed/edited | Reference specific lines, not full files |

### Cost Reduction Hierarchy

From highest to lowest impact on token efficiency:

1. **Cached input tokens**: Up to 10x cheaper than uncached input
2. **Model selection**: Can reduce costs by 40-60% per task
3. **Tool optimization**: Deferred loading saves 8-9% tokens
4. **Output compression**: Saves 40-70% on terminal output
5. **Prompt optimization**: Saves 50-70% with concise wording

### Official Pricing Reference

For detailed per-model pricing tables, see [GitHub Copilot: Models and Pricing](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing)

## Prompt Caching Optimization

### Understanding Prompt Caching

Prompt caching is one of the most powerful cost-reduction tools available in GitHub Copilot. To understand its value, let's trace through a real example from the first chat message to repeated interactions.

### How Caching Works: From First Message to Repeated Usage

#### Turn 1: Initial Chat Message (No Cache)

**What happens**:
```
User: "Help me implement user authentication in my project"

Copilot processes:
├─ System Instructions (e.g., "You are a helpful coding assistant")
├─ Copilot Custom Instructions (from .instructions.md)
├─ Tool Definitions (read, edit, terminal, git, search)
├─ Repository Context (folder structure, relevant files)
├─ File Contents (src/auth.ts, src/models/user.ts, etc.)
└─ User Message (500 tokens)
```

**Token count**: ~5,000 tokens sent to the model

**Cost**: Full price for all tokens
- System instructions: $X per 1M tokens
- Tool definitions: $X per 1M tokens
- Context: $X per 1M tokens
- User message: Charged normally

**What the model does**: Computes internal representations for every token, storing the entire "prompt state" in GPU memory.

---

#### Turn 2: Follow-up Message (Cache Miss - After 5+ minutes)

**What happens**:
```
User: "Now add email verification"

Copilot checks for cached prefix...
Cache check result: ❌ EXPIRED

Why expired?
- Default cache TTL (Time To Live) = 5-10 minutes
- User took a break
- Cache evicted from GPU memory to make room

Copilot recomputes:
├─ System Instructions (entire state recomputed) ← WASTED TOKENS
├─ Copilot Custom Instructions (recomputed) ← WASTED TOKENS
├─ Tool Definitions (recomputed) ← WASTED TOKENS
├─ Repository Context (recomputed) ← WASTED TOKENS
└─ New user message (200 tokens)
```

**Token count**: ~4,500 tokens sent (same prefix, no reuse)

**Cost**: Full price again for entire prefix
- You paid 100% for prefix tokens in Turn 1
- You pay 100% for prefix tokens in Turn 2
- **Total cost**: 2x the necessary amount

---

#### Turn 3: Follow-up Message (Cache Hit - Extended Retention Enabled)

**Prerequisites**: Enable extended cache retention (24 hours)

**What happens**:
```
User: "Add two-factor authentication support"

Copilot checks for cached prefix...
Cache check result: ✅ HIT!

Why cached?
- Extended retention enabled (24h)
- Cache moved to GPU-local storage (slower but larger)
- Prefix unchanged from Turns 1-2

Copilot reuses cached prefix:
├─ System Instructions ← REUSED (not recomputed)
├─ Copilot Custom Instructions ← REUSED
├─ Tool Definitions ← REUSED
├─ Repository Context ← REUSED
└─ New user message (250 tokens)
```

**Token count**: ~250 tokens sent to model

**Cost**: 10x cheaper for cached tokens
- Cached prefix tokens: $0.02 per 1M (vs $0.20 uncached) for GPT-5.6 Luna
- New message tokens: Charged normally
- **Total cost**: 95% reduction compared to Turns 1-2

---

#### Turn 4-10: Subsequent Messages (Continuous Cache Hit)

**Same pattern repeats**:
```
Turn 4, 5, 6, 7, 8, 9, 10: Each subsequent message reuses the same cached prefix

Cost structure:
├─ Turns 1-3: Full setup + cache miss
└─ Turns 4-10: Only new message tokens charged
   (Each costs 90-95% less than initial setup)
```

**Cumulative savings across 10 turns**:
- Without caching: ~45,000 tokens total cost
- With caching: ~15,000 tokens total cost
- **Savings**: 67% reduction

---

### Cache Invalidation: When Cache Is Lost

The cache is reset (invalidated) when any of these change:

| Change | Impact | Recovery |
|--------|--------|----------|
| System instructions modified | Full cache loss | Cache rebuilds on next request |
| Tool set changes (add/remove tools) | Full cache loss | Avoid adding tools mid-session |
| Repository context changes | Full cache loss | Keep context stable within session |
| Copilot instructions (.instructions.md) modified | Full cache loss | Update instructions between sessions |
| File content viewed | **Prefix stays, only new content added** | Cache partially preserved |
| Time expires (>24h with extended retention, >5-10min default) | Cache eviction | Enable extended retention (24h) |

### Enabling Extended Prompt Caching

#### Step 1: Locate VS Code Settings

**Method A: Via GUI**
1. Open VS Code
2. Click **File** → **Preferences** → **Settings** (or `Cmd+,` on Mac / `Ctrl+,` on Windows/Linux)
3. Search for: `prompt cache retention`

**Method B: Direct File Edit**
- **Windows**: `%APPDATA%\Code\User\settings.json`
- **Mac**: `~/Library/Application Support/Code/User/settings.json`
- **Linux**: `~/.config/Code/user/settings.json`

#### Step 2: Add the Configuration

In your `settings.json` file, add or modify:

```json
{
  "github.copilot.chat.caching.enabled": true,
  "github.copilot.chat.caching.retention": "24h"
}
```

Or alternatively (depending on VS Code version):

```json
{
  "prompt_cache_retention": "24h"
}
```

**Location in settings.json**:
```json
{
  "editor.fontSize": 14,
  "editor.formatOnSave": true,
  // ... other settings ...
  "github.copilot.chat.caching.enabled": true,        // ← Add here
  "github.copilot.chat.caching.retention": "24h",     // ← Add here
  // ... more settings ...
}
```

#### Step 3: Verify Configuration

After adding the setting:
1. Reload VS Code (File → Close Folder → Reopen or restart)
2. Start a new Copilot Chat session
3. Send first message (establishes cache)
4. Wait a few minutes and send another message
5. Notice: Second message responds faster (cache hit)

#### Step 4: Monitor Cache Effectiveness

VS Code 1.118+ shows cache metrics in some scenarios:
- Look for performance improvements in response time
- Second+ messages in session should be noticeably faster
- Run `/chronicle:cost-tips` to see cache efficiency metrics

**Diagnosis**:
- Check if instructions were modified

- Don't add/remove tools mid-session

### Strategy: Maximizing Cache Effectiveness

1. **Within a session**:
   - Keep first message detailed (establishes rich cached context)
   - Send follow-up messages that build on initial setup
   - Avoid changing instructions or tools mid-session

2. **Across multiple work days**:
   - Enable 24-hour cache retention
   - Work on same project/task for extended periods
   - Cache stays warm across morning → lunch → afternoon workflow

3. **Session architecture**:
   - One session per project feature
   - One session per debugging effort
   - One session per refactoring task
   - Each has stable cache, zero pollution between tasks

## Copilot Fusion: Intelligent Model Orchestration

### What Is Copilot Fusion?

Copilot Fusion is an intelligent runtime model router and orchestrator that automatically selects the right models and execution patterns for each task. Instead of manually choosing a specific model, you select a Copilot Fusion effort level and let it intelligently route your request through the best execution pattern.

**Key principle**: You focus on the task; Copilot Fusion handles model selection and orchestration.

### How Copilot Fusion Works

Copilot Fusion evaluates each task based on:
- Task complexity
- Reasoning requirements
- Code generation needs
- Debugging depth
- Tool usage patterns
- Real-time system health and availability

Then it selects one of three execution patterns:

| Execution Pattern | Description | When Used | Token Cost |
|-------------------|-------------|-----------|------------|
| **Single** | One model completes the entire task | Simple, well-scoped tasks | Base cost (lowest) |
| **Cascade** | Efficient model drafts solution → Judge reviews → Escalates to stronger model if needed | Medium complexity tasks where quality may need escalation | +15-30% (conditional) |
| **Critique** | One model drafts response → Multiple models critique in parallel → Original model revises based on feedback | Complex tasks requiring thorough analysis | +40-60% (but better quality) |

**Smart routing**: Different prompts in the same session can use different patterns. Copilot Fusion only adds model calls when the task warrants them.

### Copilot Fusion Effort Levels

Select the effort level that matches your task priority:

#### Fusion Standard (Recommended Default)

**Priority**: Balance cost, quality, and latency

**Use for**:
- Everyday coding tasks
- Regular refactoring
- Standard bug fixes
- Implementation work with clear requirements
- Documentation updates

**Execution pattern**: Typically single model

**Token cost**: Baseline (lowest)

**Response time**: Fast

**Example tasks**:
```
- Fix typo in variable name
- Add a new function to existing module
- Update documentation
- Format code according to standards
- Simple refactoring
```

**Use for**:

- Complex bug fixing requiring investigation
- Multi-file changes
- Tasks where additional model calls provide value

**Execution pattern**: Cascade or single model (adaptive)

**Token cost**: Baseline + 15-30% for model orchestration

**Response time**: Moderate

**Example tasks**:
```
- Fix a complex bug across multiple files
- Implement a new feature with dependencies
- Major refactoring of related modules

```

**Use for**:

## Subagents and Parallel Task Execution

### What Are Subagents?

Subagents are specialized AI agents that work independently on focused subtasks while a main orchestrator agent coordinates the overall work. This allows large, complex tasks to be broken down and executed in parallel.

**Key principle**: Main agent orchestrates → Subagents execute in parallel → Results are combined

### Main Agent vs. Subagents

| Aspect | Main Agent | Subagent |
|--------|-----------|----------|
| **Context** | Full conversation history + rich context | Only focused task context |
| **Session** | Main session with cache | Separate session, no inherited history |
| **Model** | Typically more capable | Often cheaper, focused model |
| **Responsibility** | Orchestrate, coordinate, final review | Execute assigned subtask |
| **Cache impact** | Preserves main cache | Independent cache, no interference |
| **Token cost** | Higher capability, efficient orchestration | Lower cost per subagent |

---

### When to Use Subagents

Subagents provide maximum value for:

#### Large or Complex Tasks

**Example**: Refactoring a module with 5 interdependent components

Without subagents:
```
Main agent handles all:
├─ Analyze component 1, modify, test (5,000 tokens)
├─ Analyze component 2, modify, test (4,500 tokens)
├─ Analyze component 3, modify, test (4,200 tokens)
├─ Analyze component 4, modify, test (4,800 tokens)
├─ Analyze component 5, modify, test (5,100 tokens)
└─ Total: ~23,600 tokens (sequential, slow)
```

With subagents:
```
Main agent orchestrates:
├─ Subagent 1: Component 1 (3,000 tokens) ┐
├─ Subagent 2: Component 2 (2,800 tokens) │ Parallel
├─ Subagent 3: Component 3 (2,900 tokens) │ Execution
├─ Subagent 4: Component 4 (3,100 tokens) │
├─ Subagent 5: Component 5 (3,200 tokens) ┘
└─ Main agent: Coordinate + review (2,000 tokens)
   Total: ~17,000 tokens (50% less), much faster
```

#### Parallelizable Work

**Example**: Updating dependencies across multiple services

Independent tasks that don't depend on each other:
- Service A: Update auth library
- Service B: Update database client
- Service C: Update API client

All can run simultaneously with subagents.

#### Automated Workflows

**Example**: Testing feature across multiple environments

Parallel test execution:
- Subagent 1: Unit tests
- Subagent 2: Integration tests
- Subagent 3: E2E tests
- Subagent 4: Performance tests

All running in parallel = 4x faster completion

### Using the `/fleet` Command

The `/fleet` command invokes parallel subagent execution.

#### Syntax

```bash
/fleet "Your complex task description"
```

#### How It Works

1. **Main agent analyzes**: Breaks down task into subtasks
2. **Identifies dependencies**: Determines which can run in parallel
3. **Delegates to subagents**: Assigns focused work to each
4. **Parallel execution**: Independent tasks run simultaneously
5. **Orchestrates results**: Combines and reviews outputs

#### Example 1: Multi-Module Refactoring

```bash
/fleet "Refactor user authentication: 
update src/auth/login.ts, src/auth/logout.ts, 
src/auth/verify.ts, and src/auth/refresh.ts 
to use new token format"
```

**What happens**:
```
Main agent:
├─ Plans refactoring across 4 files
├─ Identifies: All can be updated independently
└─ Delegates to 4 subagents

Subagents (parallel):
├─ Subagent 1: Refactor login.ts
├─ Subagent 2: Refactor logout.ts
├─ Subagent 3: Refactor verify.ts
├─ Subagent 4: Refactor refresh.ts

Main agent (after parallel work):
└─ Reviews all changes, ensures consistency

Result: 60-70% faster than sequential, lower cost per task
```

#### Example 2: Dependency Updates

```bash
/fleet "Update all npm dependencies in the project:
- Update package.json to latest versions
- Run npm install
- Update all import statements if needed
- Run test suite to verify"
```

**What happens**:
```
Main agent analyzes and creates plan:
├─ Task A: Update production dependencies (independent)
├─ Task B: Update dev dependencies (independent)
├─ Task C: Run tests (depends on A & B)

Execution:
├─ Subagent 1: Update production deps (parallel) ┐
├─ Subagent 2: Update dev deps (parallel)      │ Parallel
└─ Subagent 3: Run tests (waits for above)      └─→ Sequential

Result: Completes faster with intelligent dependency handling
```

#### Example 3: Testing Across Platforms

```bash
/fleet "Run comprehensive test suite:
- Unit tests on Node.js 18
- Unit tests on Node.js 20
- Integration tests on Node.js 18
- Integration tests on Node.js 20"
```

**What happens**:
```
4 parallel subagents test simultaneously:
├─ Subagent 1: Unit + Node 18 (parallel)
├─ Subagent 2: Unit + Node 20 (parallel)
├─ Subagent 3: Integration + Node 18 (parallel)
├─ Subagent 4: Integration + Node 20 (parallel)

Main agent: Collects results, reports summary

Result: 4x faster than sequential testing
```

### Cost Considerations for `/fleet`

**Benefits**:
- ✅ Faster completion (parallel execution)
- ✅ Focused context per agent (efficient)
- ✅ Cheaper subagents possible
- ✅ Scalable for large tasks

**Costs to consider**:
- ⚠️ Multiple LLM interactions (more API calls)
- ⚠️ If tasks are sequential, `/fleet` adds overhead
- ⚠️ Coordination overhead (orchestrator costs)

**When `/fleet` adds cost**:
```
Inherently sequential task:
└─ Task A → Task B → Task C (must be in order)

Using /fleet:
├─ Orchestrator: Plans, recognizes dependency chain (extra tokens)
├─ Subagent 1: Waits for Task A to finish (wasted time)
├─ Subagent 2: Waits for Task B to finish (wasted time)
└─ Result: Same time, more tokens spent

Better approach: Use main agent directly for sequential work
```

**When `/fleet` saves cost**:
```
Independent tasks:
├─ Task A (independent)
├─ Task B (independent)
└─ Task C (independent)

Using /fleet:
├─ Subagent 1: Handles Task A (4,000 tokens)
├─ Subagent 2: Handles Task B (4,000 tokens)  | Parallel
├─ Subagent 3: Handles Task C (4,000 tokens)  | 1 hour
└─ Total: 12,000 tokens in 1 hour

Without /fleet:
├─ Main agent: Task A (5,000 tokens)
├─ Main agent: Task B (5,000 tokens)          | Sequential
├─ Main agent: Task C (5,000 tokens)          | 3 hours
└─ Total: 15,000 tokens in 3 hours

Savings: 3,000 tokens (20%) + 2 hours faster

## Tool Search and Loading

### Problem: Tool Definition Overhead

Agents can access many tools:
- Built-in tools (read, edit, terminal, search, git)
- MCP server tools
- Extension-provided tools

Historically, every tool was loaded into context on every request with:
- Full name and description
- Complete JSON parameter schema

This consumes tokens even if the agent never uses most tools.

### Solution: Deferred Tool Loading

Tool search allows the model to **load tool definitions on demand**:

1. **Initial request**: Model sees only lightweight metadata (name + description)
2. **When needed**: Heavy parameter schemas load into context
3. **Cache preservation**: Deferred tools added at end of context window, keeping prefix reusable

### Performance Gains

| Model | Token Reduction |
|-------|-----------------|
| GPT-5.4 | 9.81% |
| GPT-5.5 | 8.61% |

### Best Practice

Only include tools relevant to the task. Unused tool definitions are pure token waste.

## Tool Output Compression

### Overview

Tool output compression reduces the size of command outputs sent to the model, minimizing unnecessary token consumption.

### Feature 1: `chat.tools.compressOutput.enabled`

**Purpose**: Automatically compress tool output before sending to the model

**Configuration**:
```json
{
  "chat.tools.compressOutput.enabled": true
}
```

**How it works**:
- Removes redundant lines
- Truncates verbose output
- Keeps relevant error messages and key information
- Filters out debugging noise

**Example**:
```
Before (hundreds of lines):
Build output with warnings, progress messages, unrelated logs...

After (compressed):
[10 key lines showing only errors and summary]
```

**Token Impact**: 20-40% reduction in terminal output tokens

### Feature 2: `chat.tools.terminal.outputDeltas`

**Purpose**: Send only changed portions of terminal output, not full history

**Configuration**:
```json
{
  "chat.tools.terminal.outputDeltas": true
}
```

**How it works**:
- Each turn only sends new output since last request
- Previous output stays in model's context window
- Avoids repeating static content
- Maintains full history without re-transmission

**Example**:
```
Turn 1: Send 1000 lines of initial output
Turn 2: Send only 5 new lines (the delta)
Turn 3: Send only 3 new lines (the delta)
```

**Token Impact**: 70-90% reduction in repeat output tokens

### Combined Benefit

Using both settings together:
1. Compression removes noise
2. Deltas avoid repetition
3. Model gets clean, recent information only

**Total Savings**: 40-70% reduction in tool output tokens per turn

## Cache Usage Optimization

### Preserving Cache Across Turns

Cache is your most powerful cost-reduction tool. Maximize it with these strategies:

### Strategy 1: Keep Prefix Stable

**Do**:
- Use same system instructions within a session
- Maintain consistent tool set
- Keep repository context unchanged within a task

**Don't**:
- Change instructions mid-session
- Add/remove tools frequently
- Switch models repeatedly

**Impact**: Each instruction/tool change breaks cache, resetting to full price.

### Strategy 2: Use Copilot Fusion

Copilot Fusion keeps main conversation on same model, preserving cache:
- Main agent stays on chosen model
- Reviewers/subagents use appropriate cheaper models
- Cache stays warm throughout session

### Strategy 3: Session Separation

**Use separate sessions for**:
- Different projects
- Different tasks
- Different instruction contexts
- Unrelated work

**Why**: Each session rebuild isn't cheaper, but separate sessions prevent cache pollution.

### Strategy 4: Avoid Mid-Session Model Switching

**Cost of switching models mid-session**:
1. Cache for old model is abandoned
2. New model has no cached context
3. Full price for entire request

**Better approach**:
- Use Copilot Fusion (handles model orchestration efficiently)
- Finish work with one model before switching
- Use subagents for model variety (separate cache)

### Strategy 5: Extended Cache Retention

Enable 24-hour cache retention so pauses don't break cache:

```json
{
  "prompt_cache_retention": "24h"
}
```

**Scenario**: Working on a task intermittently throughout the day
- Morning session: Cache builds up
- Lunch break: Without extended retention, cache expires
- Afternoon session: Cache still warm, saves 90% on prefix tokens

## Prompt Engineering Best Practices

### Principle 1: Be Concise with Prompts

**Before** (45 tokens):
```
Could you please help me write a Python function that reads the CSV file 
and returns a filtered dataframe where the status column is active?
```

**After** (14 tokens):
```
Write Python fn: read CSV return df where status is active
```

**Reduction**: 69% fewer tokens
**Key technique**: Remove filler words, use shorthand, be direct

### Principle 2: Provide Clear Guidance

Well-structured prompts have three qualities:

1. **Clear task definition**
   - Don't say: "fix this issue"
   - Do say: "Fix authentication failure on POST /login; returns 401 for valid credentials"

2. **Relevant context upfront**
   - Include specific files that matter
   - Mention relevant services or logs
   - Point to exact errors

3. **Clear stopping condition**
   - Define what "done" looks like
   - Prevent scope drift
   - Avoid unnecessary refactoring

### Principle 3: Examples of Concise Prompts

#### Example 1: Bug Fix
❌ Long: "There seems to be a problem with the user authentication system and I'm not sure how to fix it. Can you look at it?"

✅ Short: "Fix: auth fails on /login POST with valid credentials. Check: src/auth.ts lines 42-50"

**Token saving**: ~70%

#### Example 2: Feature Implementation
❌ Long: "I need to add pagination to our API endpoints. The API should support limiting results and I need to implement this across multiple endpoints."

✅ Short: "Add pagination to /users API: support limit/offset params, return pagination metadata"

**Token saving**: ~60%

#### Example 3: Code Review
❌ Long: "Can you review this code and let me know if there are any issues with how I've implemented the database queries?"

✅ Short: "Review src/db.ts for SQL injection risks in user queries"

**Token saving**: ~75%

### Principle 4: Output Rules

When creating agent instructions or prompts, follow these output rules:

```
# Output Rules

1. Code only – no explanation unless explicitly asked
2. No markdown preamble ("here is the code", "```")
3. No closing summaries ("I've completed this...")
4. Avoid introductory text
5. Focus on deliverable
```

**Example good instruction**:
```markdown
Write: Python function to parse JSON and validate against schema.

- Parameters: json_str, schema_dict
- Return: (bool, list[str]) for (valid, errors)
- Output: code only
```

## Agent Skills and Customization

### Caveman Skills Concept

In VS Code's Copilot extension, "Caveman Skills" refers to custom, focused instruction sets that guide agent behavior for specific tasks.

**Purpose**: Define exactly what behavior you want without lengthy explanations.

### Using Agent Files for Different Tasks

**Principle**: Use different agent instruction files (`.agent.md`, `.instructions.md`) for different task types.

**Structure**:
```
project/
├── .instructions.md           # General project instructions
├── .agent-code-review.md      # Custom code review agent
├── .agent-implementation.md   # Custom implementation agent
├── .agent-debugging.md        # Custom debugging agent
└── .agent-research.md         # Custom research agent
```

### Example: Code Review Agent File

Create `.agent-code-review.md`:
```markdown
---
description: Focused code review agent
---

# Code Review Agent

## Scope
Review staged changes for security, performance, and correctness issues.

## Rules
1. Focus on logic errors only
2. Flag SQL injection, XSS vulnerabilities
3. No style suggestions
4. Suggest fixes for critical issues
5. Output: bullet-list format

## Do Not
- Refactor unrelated code
- Add new features
- Change working code
- Request changes to passing tests
```

### applyTo Pattern

Limit agent instruction scope to specific files:

```markdown
---
applyTo:
  - "**/*.test.ts"
  - "src/services/**"
  - "!src/legacy/**"
description: Test and service layer rules
---
```

This prevents irrelevant instructions from consuming tokens on unrelated files.

### Excluding Files from Context

Reduce token usage by excluding files from search/edit:

**In VS Code settings**:
```json
{
  "copilot.excludeFiles": [
    "**/node_modules/**",
    "**/.git/**",
    "**/dist/**",
    "**/build/**",
    "**/*.lock"
  ]
}
```

**In workspace settings** (`.vscode/settings.json`):
```json
{
  "files.exclude": {
    "**/*.log": true,
    "**/temp/**": true,
    "**/.cache/**": true
  },
  "copilot.exclude": [
    "vendor/**",
    "third-party/**"
  ]
}
```

**Impact**: Prevents agent from including unnecessary files in context, saving 10-30% tokens per request.

## Practical Tips and Techniques

### Tip 1: Keep Sessions Short and Focused

**What**: Complete one task per session, then start a new session

**Why**:
- Each session accumulates history
- History is sent with every request (unless cached)
- Unrelated history pollutes context

**Example**:
- Session 1: Add authentication feature
- New session: Implement user profile page
- New session: Fix bug in payment flow

**Token savings**: 20-40% per subsequent turn

### Tip 2: Treat Instructions Like Code

**Principle**: Keep instructions clean, modular, and maintainable

**Do**:
- Use consistent formatting
- Group related rules
- Use clear section headers
- Version control instructions

**Don't**:
- Mix unrelated rules
- Use vague language
- Include examples within rules
- Update instructions mid-session

**File structure**:
```
project/
├── .instructions.md           # Core rules
├── .agent.md                  # Agent behavior
└── docs/INSTRUCTIONS.md       # Full documentation
```

### Tip 3: Reference What You Need

**Strategy**: Point agent to specific files/lines instead of pasting content

**Before** (includes full file):
```
I need help with this file:
[paste 500 lines of code]
```

**After** (specific reference):
```
Debug src/auth.ts lines 42-60, specifically the verifyToken function
```

**Token savings**: 70-90%

### Tip 4: Match Model to Task Complexity

| Task | Recommended Model | Reasoning |
|------|-------------------|-----------|
| Refactor function | Claude Haiku 4.5 | Simple structural change |
| Fix bug with logs | GPT-5.6 Luna | Quick analysis needed |
| Implement feature | GPT-5.6 Terra | Balanced approach needed |
| Design architecture | GPT-5.6 Sol | Deep reasoning required |
| Long-running agent | GPT-5.3-Codex | Autonomous task handling |

### Tip 5: Use Agent Mode for Complex Tasks

**When to use Agent Mode**:
- Multi-file refactoring
- Long-running implementations
- Tasks requiring multiple iterations
- Complex debugging with tool usage

**How to enable**:
- Toggle "Agent" in Copilot Chat
- Or use keyboard shortcut
- Or use `/agent` command

**Why it helps**:
- Background Todo Agent manages progress
- Extended context window available
- Tool use is optimized
- Better at multi-step tasks

**When NOT to use**:
- Simple questions
- Single-file edits
- Quick refactoring
- Status checks
